# Pedidos do iFood (parte 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** iFood orders reach Gastrux by themselves (polling the iFood Merchant API every 30 s), go through the order
pipeline of part 1 to the kitchen, Caixa and DRE, and every status change goes back to iFood, ready for homologation.

**Architecture:** `lib/ifood/` holds the HTTP client (tokens, endpoints, a replaceable transport), the order mapper
(iFood order → `OrderApiInput` + extra ticket lines) and the event processor. A loop started from `instrumentation.ts`
polls every 30 s. Status changes made in Gastrux reach iFood through one hook, `pushPlatformStatus`, called from the
existing accept/reject/followKitchen paths, so parts 2 (Keeta, 99Food) plug into the same place later.

**Tech Stack:** Next.js 14.2 (app router, `instrumentation.ts` with `experimental.instrumentationHook`), Prisma +
PostgreSQL, Jest (unit and integration configs), `lib/security/credential-crypto.ts` for tokens at rest.

**Spec:** `docs/superpowers/specs/2026-10-24-ifood-design.md` (and the general design
`docs/superpowers/specs/2026-10-23-delivery-plataformas-design.md`)

## Global Constraints

- iFood only on the Business plan: `isTierFeatureEnabled(tier, 'deliveryPlatforms')` (trial is Business).
- Connect/disconnect/pause: only OWNER and MANAGER (`MANAGER_ROLES`); test-mode linking: only `requirePlatformAdmin()`.
- iFood customers never go to the CRM and never earn cashback (`OWN_CUSTOMERS` stays `gastrux_api`, `delivery_site`).
- Polling interval 30 s, never faster; one in-flight poll at a time.
- Ack an event only after it is stored and processed; a failed event is not acked (iFood repeats it).
- Renew a token only when it expired or iFood answered 401, never in advance.
- Confirm on iFood within 8 minutes: auto-accept confirms at once; "Aceitar" confirms; a failed confirm is retried by
  the next poll while the order is CONFIRMED and `platformConfirmedAt` is null.
- Sale value: items + options; + delivery fee only when `deliveredBy === 'MERCHANT'`; − benefits sponsored by
  `MERCHANT`. iFood-sponsored coupons do not reduce it. `additionalFees` ignored.
- Env: `IFOOD_CLIENT_ID`, `IFOOD_CLIENT_SECRET`, `IFOOD_APP_MODE` (`centralized` | `distributed`, default
  `distributed`), `IFOOD_POLLING` (`on` to start the loop), base URL `https://merchant-api.ifood.com.br`.
- Every feature updates `lib/ai/knowledge/*.ts` and `lib/help/seed-articles.ts`; a changed default text keeps its old
  sha256 in `LEGACY_DEFAULT_HASHES`. Deferred items go in full to `docs/pendencias.md`.
- Files use CRLF; copy in plain Portuguese.

## Review Focus

1. The same PLC event twice in one poll and again in the next poll: one ExternalOrder, one kitchen order, both acked.
2. Processing throws for one event (DB down mid-poll): that event is not acked, the others are; the next poll recovers it.
3. A centralized token sees a merchant that is not linked to any restaurant (or linked to a plan-locked one): its
   events are acked and dropped, and never create an order in another restaurant.
4. iFood answers 401 in the middle of a poll: one renewal, one retry, no loop of renewals.
5. An order cancelled by iFood after the kitchen finished it (COMPLETED): no crash, the sale stays, a bell alert says
   iFood cancelled a finished order.

Each line has its test in the owning task (Tasks 5 and 2).

### Task 5: Event processing and one poll

**Files:**
- Create: `lib/ifood/events.ts`
- Test: `__tests__/integration/api/ifood-events.test.ts`

**Interfaces:**
- Consumes: Tasks 2–4.
- Produces:
  - `pollIfoodOnce(): Promise<{ events: number; acked: number; failed: number }>`:
    1. linked integrations = `platform 'ifood'`, `isActive`, `storeId` set, restaurant `restaurantAcceptsOrders` and tier `deliveryPlatforms`;
    2. centralized: one `pollEvents(null, allMerchantIds)` in chunks of 100; distributed: one per integration;
    3. each event: `ifoodEvent.createMany({ skipDuplicates })`; then, if `processedAt` is null, `processIfoodEvent`;
       success sets `processedAt`, failure sets `error` and leaves it unacked;
    4. ack every event of this poll whose row has `processedAt`;
    5. integration `lastPolledAt = now`, `syncStatus SUCCESS`, or `ERROR` + `syncError` when the poll call failed;
    6. retry `confirm` for its orders CONFIRMED with `platformConfirmedAt` null and `orderReceivedAt` within 8 min;
    7. iFood orders still PENDING 5 min after `orderReceivedAt` ring a second HIGH bell
       "O pedido iFood #<displayId> espera o Aceitar: o iFood cancela em 8 minutos" (dedupeKey `ifood-waiting-2:<id>`, once).
  - `processIfoodEvent(event, integration | null)` by `code`:
    - merchantId without a linked integration → processed, nothing done (Review Focus 3);
    - `PLC` → `getOrder` + `mapIfoodOrder` + `ingestDeliveryOrder({ platform: 'ifood', ... })`;
    - `CFM` → if still PENDING, `acceptDeliveryOrder(..., { fromPlatform: true })` and `platformConfirmedAt = now`;
    - `SPS`/`RTP`/`DSP` (changed by another system) → forward-only status (PREPARING/READY/PICKED_UP) without pushing back;
    - `CAN` → ExternalOrder CANCELLED; kitchen order `cancelOrder` with `fromPlatform`; if it was COMPLETED, keep it and
      raise a CRITICAL bell "O iFood cancelou o pedido #<displayId>, que a cozinha já concluiu";
    - `CON` → ExternalOrder DELIVERED;
    - `HSD` (handshake dispute) → save `disputeId`, `disputeExpiresAt` (from `metadata`), HIGH bell
      "O cliente pediu para cancelar o pedido iFood #<displayId>: responda em Pedidos de delivery"; `HSS` → clear `disputeId`;
    - `CARF` (cancellation request failed) → HIGH bell "O iFood não aceitou o cancelamento do pedido #<displayId>";
    - anything else → processed, logged only.
