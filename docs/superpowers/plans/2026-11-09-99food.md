# Pedidos da 99Food Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 99Food orders arrive in Gastrux by webhook, go through the existing delivery pipeline (accept, kitchen, Caixa), and Gastrux sends confirm/ready/delivered/cancel/answers back; the restaurant links its 99Food store and pauses it from Gastrux.

**Architecture:** `lib/ninetynine/` mirrors `lib/ifood/`: a client (signing, bigint-safe JSON, per-store token with refresh), an order mapper to `OrderApiInput`, an event table filled by the webhook route (store, answer `errno 0`, process later) and a worker loop started from `instrumentation.ts`. `lib/delivery-orders/platform-sync.ts` becomes platform-aware so the kitchen and Pedidos de delivery drive iFood and 99Food through one door. iFood behaviour must not change.

**Tech Stack:** Next.js 14, Prisma (Postgres), `json-bigint` (new dependency), Node 20 in production, Jest.

**Spec:** `docs/superpowers/specs/2026-11-09-99food-design.md` (approved 2026-11-09; read its last section "Atualização depois da leitura da referência").

## Global Constraints

- Base URL from env `NINETYNINE_FOOD_BASE_URL` (default `https://openapi.99food.com`); credentials `NINETYNINE_FOOD_APP_ID`, `NINETYNINE_FOOD_APP_SECRET`; worker on only with `NINETYNINE_FOOD_EVENTS=on`. Missing app id/secret → integration shows "não configurada" and nothing is called.
- IDs (`app_id`, `order_id`, `shop_id`, `apply_id`) are 64-bit: parse every 99Food response and webhook with `json-bigint` (`useNativeBigInt` or `storeAsString`), keep them as **strings** in Gastrux, send them back as JSON number literals (bigint stringify). Never `JSON.parse` a 99Food body.
- Request auth: `auth_token` per store (GET `v1/auth/authtoken/get` / `v1/auth/authtoken/refresh` with `app_id`, `app_secret`, `app_shop_id`; limit 1 req/30 s each; refresh cooldown 2 min). On `errno 10102` (expired) or `10101`: refresh, get, retry the call once. App-level v3 calls carry `app_id`, `timestamp`, `sign` = MD5(sorted `k=v` joined by `&` + app_secret; arrays/objects as `Array`; empty values left out).
- Webhook: header `didi-header-sign` must equal MD5(raw body + app_secret); answer `{"errno":0,"errmsg":"ok"}` within 6 s **after storing** and before processing; bad signature → 401, nothing stored.
- Confirm within **5 minutes** of `orderNew`. Sino on arrival and again at 3 min.
- Plan gate exactly like iFood: `isTierFeatureEnabled(tier,'deliveryPlatforms')` and `restaurantAcceptsOrders`; dono e gerente connect.
- Money: prices in cents → reais (÷100). Sale = items + modifiers, + delivery fee only when `delivery_type` = 2 (store delivery), − promotions paid by the store (`shop_subside_price`); 99Food-paid promotions don't reduce the sale. Commission out.
- Ticket/screen/receipt show `order_index` (number) and `order_id` (code) — 99Food go-live requirement.
- Cancel reason list (pt-BR labels, ids fixed): 1010 Item esgotado; 1020 Loja fechada por hoje; 1030 Loja sem condições de preparar agora (muito movimento); 1040 Acidente ou falta de energia/água; 1050 Problema com o cliente; 1060 Sem entregador (só entrega própria); 1070 Cardápio precisa ser atualizado; 1071 Fora da área de entrega (só entrega própria); 1072 Endereço em área insegura (só entrega própria); 1073 Suspeita de fraude ou trote; 1074 Dúvida sobre taxas ou promoções; 1080 Outro motivo (texto obrigatório).
- Keep events and request ids 30 days. Tokens encrypted with `lib/security/credential-crypto` (same as iFood).
- Every client-facing feature updates `lib/ai/knowledge/delivery.ts` and `lib/help/seed-articles.ts` (hash rule).
- iFood paths keep passing their existing tests unchanged.

## Review Focus

1. **The same `orderNew` delivered twice, or the worker running in two processes** — one ExternalOrder, one confirm. Test in Task 4 (`duplicate orderNew → one order, one confirm`) and a lease like iFood's.
2. **A 19-digit order id** — survives webhook → DB → confirm call byte-for-byte. Test in Task 1 (`bigint round trip`) and Task 4.
3. **Token expired in the middle of a confirm** — refresh + retry once, no double confirm. Test in Task 1.
4. **A store linked to restaurant A sending an event, but the integration is paused/disconnected or on a locked plan** — not ingested, still answered `errno 0`, logged. Test in Task 4.
5. **Pickup orders (`fulfillment_mode` 1) and privacy-masked addresses** — mapped as "Retirada" / masked text without crashing. Test in Task 3.

**Interfaces:**
- Produces:
  - `parseBig(raw: string): any` (big ints → strings), `stringifyBig(value: unknown, bigKeys: string[]): string` (writes the listed keys' string values as number literals).
  - `signParams(params: Record<string, unknown>, secret: string): string`; `verifyWebhookSign(rawBody: string, header: string | null, secret: string): boolean` (timing-safe compare, lowercase hex).
  - `ninetynineConfig(): { baseUrl: string; appId: string; appSecret: string } | null`
  - `class NinetynineError extends Error { errno: number; requestId?: string }`
  - `tokenFor(integrationId: string, renew?: boolean): Promise<string>` — reads/stores encrypted token in `DeliveryIntegration.oauthAccessToken` + `oauthExpiresAt` (from `token_expiration_time`); `storeId` holds `app_shop_id`.
  - `storeCall<T>(integrationId: string, path: string, body: Record<string, unknown>, opts?: { method?: 'GET'|'POST'; bigKeys?: string[] }): Promise<T>` — adds `auth_token`; on errno 10101/10102 refreshes and retries once.
  - `appCall<T>(path: string, body: Record<string, unknown>): Promise<T>` — v3 signed calls.
  - Endpoint helpers: `getAuthorizationUrl(): Promise<string>`, `listAuthorizedShops(page: number, size?: number)`, `getOrderDetail(integrationId, orderId)`, `confirmOrder`, `orderReady`, `orderDelivered`, `cancelOrder(integrationId, orderId, reasonId: number, reason?: string)`, `answerCancelApply(integrationId, orderId, applyId, agree: boolean, reason?: string)`, `answerRefundApply(integrationId, orderId, applyId, agree: boolean, refuse?: { baseReasonId: string; baseReason: string })`, `confirmCashPayment(integrationId, orderId)`, `setStoreStatus(integrationId, status: 'online' | 'pause')` (pause = `store_status 3, pause_time 4, pause_reason_code 1006`), `setConfirmMethod(integrationId, method: 1 | 2)`.
  - Every response's `requestId` is returned/logged for support.

  - `shopStatus` → `syncStatus`/`syncError` from `sub_biz_status` (1 open; 2 paused; 3 closed; 4 disconnected; 5 out of hours; 6 blocked; 7 no riders) shown on the integration screen.
